Context

Who owns the cart

Context is not “global state”. It is one specific thing: one value, owned in one place, read by components that are nowhere near each other. In this app that value is the cart.

2 After: the provider publishes, the readers ask

Three components, one value, no wiring between them.

CartProvider useState(cart) lives here now

value = {{ cart, addToCart, count, total }}

Header const {{ count }} = useCart()
ShopPage const {{ addToCart }} = useCart()
CartPage const {{ cart, total }} = useCart()

The provider is still above them in the tree. The data still flows one way. The only thing that changed is that the components in between no longer carry it.

3 What actually re-renders

Press “add to cart” in each mode. Then read the caption — it is not the story you expect.

0 re-rendered
App owns page
Header useCart()
ShopPage useCart()
CartPage useCart()

With props, App re-renders and hands new values to all three children.

Do not sell context as a performance tool. Every consumer still re-renders on every change, and there is no selector to opt out. Here it buys three fewer props and an App that no longer knows what a cart is. That is the honest reason to use it.

4 Use it when…

good fit
  • one value is read by components in different branches of the tree
  • the signed-in user
  • the cart / basket
  • theme, locale, currency

Several distant readers, few writers.

not a fit
  • a value one page uses — that is local state
  • a value one child needs — that is a prop
  • server data — that is a hook’s job
  • “everything, in one big provider”

If only one component reads it, context is overhead.

5 Three files, in this repo

1 · the owner context/CartContext.jsx

Holds the state, the three actions, and the derived count and total.

2 · the reader components/Header.jsx

Reads count. Has no props related to the cart.

3 · the other reader pages/CartPage.jsx

Reads cart and total. Same provider, different branch of the tree.
